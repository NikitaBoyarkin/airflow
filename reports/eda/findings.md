# EDA Findings — Airflow DAG outputs (`data/out/*.csv`)

**Дата:** 2026-10-13
**Полный отчёт:** `reports/eda/eda-airflow-2026-10-13.md`

## Датасет вкратце

Выходные CSV проекта `airflow` (derived surface): 5 дневных файлов `sales_report_*`
(100 строк, одна строка = `sale_date` × `product_id`) и 3 недельных
`weekly_sales_summary_*` (12 строк, одна строка = `week_start` × `category`).
Период: 2026-08-31 … 2026-09-05 (дневной), 2026-08-23 … 2026-08-30 (недельные окна).
Качество значений — хорошее (0 пропусков, 0 дубликатов, revenue/orders ≥ 0);
качество **непрерывности периодов** — плохое (пропуск дня, неполный последний день,
перекрывающиеся недельные окна).

## Топ проблем качества

### Проблема 1: Последний дневной период неполный (2026-09-05)
- **Что:** `sales_report_2026-09-05.csv` — revenue 4.12M против ~25.5M у соседей (**−83.9%**), orders 1,612 против ~10,000, при неизменном `avg_price` (~2,556).
- **Влияние:** если читать как тренд — ложный «обвал продаж»; все 20 IQR-выбросов дневного профиля приходятся на этот день.
- **Действие:** флаг `is_partial` для последнего окна; исключать из трендов/алертов до закрытия суток.
- **Владелец:** дата-инженер.

### Проблема 2: Разрыв непрерывности дат — пропущен 2026-09-03
- **Что:** дневные файлы покрывают 5 из 6 дней диапазона; 09-03 отсутствует. `catchup=False` (`dags/daily_sales_report.py:146`) не догоняет пропуск автоматически.
- **Влияние:** дневной ряд нельзя считать непрерывным; агрегаты за окно неполны.
- **Действие:** проверка покрытия дат в `scripts/metrics_report.py` + алерт; точечный `airflow dags backfill` для 09-03.
- **Владелец:** дата-инженер.

### Проблема 3: Недельные окна перекрываются
- **Что:** `week_start` = 08-23, 08-29, 08-30 (шаги 6 и 1 день). Окна `[08-23,08-30)`, `[08-29,09-05)`, `[08-30,09-06)` перекрываются; `weekly_window` = `logical_date − 7`.
- **Влияние:** суммирование недель двойной счёт (06 дней пересечения у 2-го и 3-го); max/min итогов ×8.23 вводит в заблуждение.
- **Действие:** писать `window_start`/`window_end` в CSV; ключевать по `logical_date`; дедуплицировать при агрегации.
- **Владелец:** дата-инженер.

### Проблема 4: `revenue` — производная `orders` (мультиколлинеарность)
- **Что:** r(`revenue`,`orders`) = **0.9972**, `avg_price` ∈ [2,537; 2,556] на всех файлах → `revenue ≈ orders × 2,550`.
- **Влияние:** `revenue` и `orders` — одна мера; совместное использование в модели некорректно.
- **Действие:** в аналитике брать одну из двух; документировать `amount`-семантику.
- **Владелец:** аналитик.

### Проблема 5: Сегментного сигнала нет (принять как свойство демо-данных)
- **Что:** gap по `product_id` ×1.12, по `category` ×1.03 — ниже порога 1.5; разрыв не объясняется составом (все продукты во всех днях).
- **Влияние:** продуктовых/категорийных инсайтов в демо-данных нет; искать их здесь бессмысленно.
- **Действие:** для реального кейса — источник Postgres с дифференцированным `amount`/`category`.
- **Владелец:** бизнес-заказчик / дата-инженер.

## Что в порядке

- 0 пропусков, 0 полных дубликатов, 0 дубликатов по ключу во всех 8 файлах.
- `revenue` и `orders` ≥ 0 и в правдоподобном диапазоне; отрицательных нет.
- Заголовки файлов совпадают с DQ-контрактом (`DEFAULT_HEADER` / `WEEKLY_HEADER`).
- `product_id` — ровно `p1`…`p20` (20); `category` — ровно 4 ожидаемых.
- Даты в диапазоне [start_date 2026-01-01, сегодня]; будущих нет.
- Суммы по `product_id`/`category` сходятся с агрегатами дней/недель.
- README-claims «2 DAG-а» и «64 теста» воспроизводятся.
